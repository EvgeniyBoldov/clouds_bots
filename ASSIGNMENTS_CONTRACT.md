# Поручения между Clouds и Почемучкой

Этот документ фиксирует целевой контракт push-доставки. В текущем коде
Копатыч забирает события из Почемучки по курсору. Для переключения нужно
подключить callback в Clouds и исходящую доставку в Почемучке.

Clouds принимает аутентифицированное событие eXpress BotX, проверяет разрешение
`use` для Копатыча и передаёт поручение Почемучке. Почемучка сверяет
полномочия коннектора и аккаунт пользователя, закрепляет владельца
и tenant, выдаёт `run_id` и исполняет поручение. Clouds привязывает
`run_id` к BotX-аккаунту, автору, чату и исходному sync ID.

## Аутентификация и привязка

Коннектор передаёт `Authorization: Bearer <connector-secret>` и
`X-Assignment-Connector: clouds:express`. Коннектор из заголовка должен
совпадать с `source` на входе. Секрет настраивается в привязанной внешней
системе Clouds как Bearer. Почемучка получает его в
`ASSIGNMENT_CONNECTOR_TOKENS` в JSON-словаре `{"clouds:express":"…"}`.
Используйте стабильный `GATEWAY_KOPATYCH_CONNECTOR_ID` на весь срок
жизни привязок и запущенных поручений. Если CTS имеют разные пространства
HUID, заведите им разные идентификаторы коннектора.

При наличии связи portal ищет пользователя по `(source, user.clouds)`.
При первом обращении Копатыч начинает с UUID. На
`403 identity_not_linked` он получает почту из записи CTS по AD
логину и домену автора через CTS с проверкой TLS, сверяет HUID той записи с HUID входящего события
и повторяет запрос с `user.mail`. Почемучка связывает UUID с одним
активным LDAP-пользователем, который уже входил в портал и имеет активный
tenant. Повторное совпадение по почте при уже занятой привязке не меняет
владельца. Пользователь без связи или активного tenant получает
инструкцию войти через LDAP и проверить доступ.

Ключи `mail`, `clouds`, `telegram`, `tel` обозначают типы идентификаторов.
В первой версии аутентифицированный Clouds вправе утверждать свой HUID
и почту для первой привязки. `telegram` и `tel` предусмотрены в схеме.
Для аутентификации такими ключами понадобится отдельный проверенный
резолвер. Произвольный ключ или переданное значение сами по себе прав
не предоставляют.

## Приём

`POST /api/v1/integrations/assignments` принимает:

```json
{
  "source": {"type": "clouds", "id": "express"},
  "event_id": "46f77f78-a721-468e-88da-3fdfd27524f1",
  "user": {
    "mail": "test@example.org",
    "clouds": "c353bde2-f196-45b5-8aff-1c55ed5a1c7f",
    "telegram": 12312451235,
    "tel": "+15724473200"
  },
  "data": {"text": "Проверь заявку завтра", "timezone": "Europe/Moscow"},
  "reply_to": {
    "type": "clouds",
    "id": "express",
    "data": {
      "bot_id": "0cb85b3b-dd78-4466-ad39-5aa42876d206",
      "chat_id": "786f8b8e-3a44-4a20-b227-cc900605c88a",
      "message_id": "46f77f78-a721-468e-88da-3fdfd27524f1"
    }
  }
}
```

Достаточно `clouds` для связанного автора. `data.referenced_context`
может содержать явно приложенную цитату. Clouds передаёт локальный
`request_id` как `event_id` и использует его при повторах.
Портал возвращает HTTP 202 с `run_id`, `chat_id`,
`event_id` и `status`. Повтор того же входного события возвращает тот же
run. Изменение входа или маршрута для принятого события даёт HTTP 409.

## Ответ и отмена со стороны Clouds

Пути относительны к коллекции Почемучки `/api/v1/integrations/assignments`.

| Операция | Контракт |
| --- | --- |
| `POST /{run_id}/responses` | Входной коннектор посылает `user`, `event_id`, `pause_id`, `value` как строку или JSON boolean. Почемучка сверяет исходного автора и паузу. |
| `POST /{run_id}/cancel` | Входной коннектор посылает `user` и `event_id`. |

Clouds сохраняет локальный `request_id` и привязку к BotX-аккаунту,
автору, чату и исходному сообщению до обращения в Почемучку. Из ответа
на приём сохраняется внешний `run_id` в пределах внешней системы.
Запуск Копатыча в новом процессе восстанавливает привязку из `kopatych_runs`.
Ответ пользователя на уточнение сопоставляется с BotX sync ID
отправленного вопроса и его `pause_id`.

## Push-доставка из Почемучки в Clouds

После завершения итерации или фазы, когда runtime решил сообщить вопрос,
промежуточный результат либо итог, Почемучка фиксирует событие в
транзакции состояния поручения. Отдельный отправитель Почемучки вызывает
`POST /api/v1/integrations/assignments/events` на стороне Clouds.
Следующий этап выполнения может начаться после фиксации события.

Адрес callback и секрет для направления Почемучка → Clouds задаются
администратором для каждого разрешённого `reply_to.type:id`. URL
поступает из конфигурации, а `reply_to.data` описывает адрес в системе
адаптера. Для Копатыча окончательный адрес треда берётся из локальной
привязки `run_id`. Вызов передаёт API-ключ обратного направления в `X-API-Key`
и `X-Assignment-Connector` с ID получателя, например `clouds:express`.
В Clouds API-ключ выпускается для внешней системы с назначением
`assignment_events`. Push принимается для поручений, созданных в режиме
`GATEWAY_KOPATYCH_DELIVERY_MODE=push`.
Clouds проверяет, что привязка поручения относится к этому коннектору.
Если на приёме явно разрешён другой обратный коннектор, Почемучка
отправляет событие на его настроенный callback.

Пример промежуточного результата для поручения, которое ждёт таймера:

```json
{
  "run_id": "ebc355ac-6296-4cc1-b692-6f5ac4fabede",
  "event_id": "ad219758-206e-4f3c-97ef-bc28dad50055",
  "sequence": 1,
  "kind": "progress",
  "status": "waiting_timer",
  "result": {
    "text": "Заявка в работе. Следующая проверка в 10:00.",
    "wake_at": "2026-11-27T07:00:00Z"
  }
}
```

`event_id` стабилен для повторов. `sequence` начинается с 1 и
увеличивается для каждого **callback-события этого поручения**.
Тихая итерация или сон без пользовательского обновления не создаёт
callback. `status` отражает состояние поручения при фиксации события,
а `kind` определяет, что должен сделать Копатыч.

| `kind` | Допустимый `status` | Значение и данные |
| --- | --- | --- |
| `progress` | `running`, `waiting_timer` | Промежуточное сообщение из `result.text`. Для сна можно добавить `result.wake_at`. Привязка остаётся активной. |
| `question` | `waiting_input`, `waiting_confirmation` | Вопрос в `result.text`, обязательные `result.pause_id` и `result.response_schema`. После публикации Копатыч сохраняет связь BotX sync ID вопроса с паузой. |
| `final` | `completed`, `failed`, `cancelled` | Терминальный исход. При `completed` передаётся итоговый `result.text`. При ошибке или отмене можно передать безопасный текст, иначе Clouds использует стандартное уведомление. |

Ответ на первоначальный приём уже содержит `status`, обычно `queued`.
Clouds сохраняет последний полученный статус вместо вывода состояния из
текста. Финальный `kind` закрывает локальное ожидание продолжения.
Отказ в подтверждении передаётся как значение ответа на `pause_id`.
Он может привести к новой итерации планера.

### Подтверждение и повторы

1. Clouds проверяет секрет и привязку, затем атомарно сохраняет входящее
   событие и ставит локальную отправку в BotX в очередь. HTTP 202 означает,
   что Clouds взял ответственность за доставку. Подтверждение отправки
   пользователю приходит из BotX и хранится в Clouds отдельно.
2. Если callback повторён с тем же `event_id` и содержимым, Clouds
   возвращает HTTP 202 без второй задачи отправки. Повтор ID с другим
   содержимым даёт HTTP 409 с кодом `event_conflict`. Новый callback после
   принятого финала даёт HTTP 409 с кодом `assignment_closed`; точный
   повтор уже принятого события по-прежнему получает HTTP 202.
3. Если событие пришло раньше сохранения привязки `run_id`, Clouds
   возвращает HTTP 409 с кодом `binding_pending`. При пропуске номера
   возвращает HTTP 409 с кодом `sequence_gap` и ожидаемым номером.
   Почемучка повторяет сохранённое событие после временного сбоя,
   сетевой ошибки или этих двух ответов, сохраняя исходные
   `event_id` и `sequence`. Отправитель соблюдает порядок внутри run.
4. Копатыч публикует промежуточные события и финал в исходное сообщение
   BotX. Clouds сохраняет sync ID опубликованного ответа. Временный сбой
   BotX приводит к локальному повтору доставки. Сбой между BotX-отправкой
   и сохранением её sync ID оставляет риск повторной публикации.
