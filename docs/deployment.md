# Production delivery

The delivery flow follows ML-Inference-Service: `make release-preview` calculates the next release and dependency base; `make release` requires a clean worktree and upstream, builds and pushes immutable version and commit tags, records the pinned base digest and Alembic head in `release.env`, then commits and pushes that manifest. Configure `REGISTRY`, `IMAGE`, and the blue/green ports in the manifest before the first release. The registry must be reachable and authenticated from both the release machine and production host. GitLab deploys manifest changes on the default branch; rollback is a manual pipeline job.

On the production host, install Docker Compose, nginx, curl and flock. Create the external Docker network `clouds-bots-runtime`. Install `scripts/production-controller.sh` as `/usr/local/sbin/clouds-bots-deploy`, owned by root and mode 0750, and permit the `production-shell` GitLab runner to invoke that controller through passwordless sudo. Create `/opt/clouds-bots/releases` and `/etc/clouds-bots` owned by root. Create `/etc/clouds-bots/controller.env` as root:root mode 0600 with `CI_BUILDS_ROOT` pointing to the runner checkout parent. The controller itself must be updated by an administrator when it changes.

Create `/etc/clouds-bots/runtime.env` with the settings from `.env.example` plus `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD`. Set `GATEWAY_DATABASE_URL` to the corresponding PostgreSQL credentials and host `postgres`, and set `GATEWAY_ADMIN_COOKIE_SECURE=true` for HTTPS. Protect this file as a secret.

For production HTTPS, make ports 80 and 443 available to the host nginx. Provision the certificate chain at `/etc/clouds-bots/tls/fullchain.pem` and private key at `/etc/clouds-bots/tls/privkey.pem` separately from deployment; restrict the private key to the nginx master process (normally root:root, mode 0600). Set the real hostname in both `server_name` directives in `infra/nginx-production.conf`, then install it as `/etc/nginx/conf.d/clouds-bots.conf`. HTTP redirects to HTTPS, and nginx terminates TLS and proxies requests to the active slot. Use distinct hostnames when sharing nginx with other services.

The deployment controller writes `/etc/nginx/conf.d/clouds-bots-upstream.conf`; initialize it to one of the slot ports before validating nginx for the first time. Ensure nginx loads both configuration files in its HTTP context, then run `sudo nginx -t` and `sudo systemctl reload nginx`. Repeat the validation and reload after renewing the certificate.

Deployments run migrations before starting the candidate, check `/health/ready`, switch nginx, and retain the previous release for rollback. Database migrations must remain compatible with both versions: rollback switches application images and does not reverse migrations. Existing installations must migrate their data into the `clouds-bots-postgres-data` volume before switching traffic. Choose ports that do not conflict with other services, including ML-Inference-Service. This repository's local Compose stack remains available for development.

Only one gateway process owns the queued-message worker at a time. PostgreSQL advisory locking transfers ownership when the old release stops; interrupted processing jobs are recovered by the new owner. As with any external message delivery, a crash after sending but before recording completion can still cause a retry.
